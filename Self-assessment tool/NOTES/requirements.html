This is the standing record of what the GC Enterprise Architecture self-assessment tool has to do. It accumulates: a decision made in a meeting is written here the same day, with who made it.

Each requirement carries a number so it can be quoted, a state, and an owner where somebody owes an answer. Numbers are never reused and never renumbered. Nothing is deleted when a requirement changes: the state changes and the reason goes in the note.

Owners are named people. Build team means Mariia Yermolenko, who is building this on a co-op term at the Treasury Board Secretariat. TBS means whoever holds the decision inside the department, which is Dan Cooper unless the entry says otherwise.

What this follows, and where it departs

The standard. ISO/IEC/IEEE 29148:2018, Systems and software engineering, life cycle processes, requirements engineering. It replaced IEEE 830, which is withdrawn and still the thing most people picture when they hear the words requirements specification.

Tailored, which the standard allows. Clause 4.5 permits tailoring. Two departures are deliberate. The document carries a status line where a signature block would go, because it is living and gets baselined at each release. And requirements are written in plain present tense, leaving out the "shall" convention in clause 5.2.7, because the people who read this are two colleagues and a director, and "the tool shall keep work as it is typed" is harder to read than the same sentence without it.

States. Proposed is the standard word. Agreed means analysed, agreed by whoever owns the decision, and committed to. Built means it is in the tool. Open marks a decision nobody has made, and every open item is also listed in one place at the top.

1. Purpose and scope

What the tool replaces and what it does not touch.

P1 A department scores its own architecture against the published GC Enterprise Architecture framework and points at evidence it already holds. Agreed Replaces the GC EARB assessment template and the score deck built by hand.
P2 The assessor reads the answers that do not add up. Reading all 176 is the job this abolishes. Agreed On a full submission the anomalies are single digits out of 176 questions.
P3 Everything in the tool is unclassified. Nothing protected or classified goes into it at all. Agreed Settled with Dan on 1 September 2026. This one decision removes the second deployment, the local-only mode, the theme switch and the recall problem.
P4 Which initiatives have to submit one. Open Dan owes this Blocks nothing that is being built.

2. Roles and access

Three roles, and three views that do not overlap. The prototype shows them in one page because it is a prototype.

R1 Three roles: submitter, assessor, admin. Agreed
R4 Neither side offers a way into the other. Built The submitter home page carried two links across, to the assessor view and to the admin view. They existed to make testing easy before either side worked, and they offered a person who is not an assessor a sign-in they cannot pass. The addresses still reach both, which is how the tests get there. Admin stops being a destination of its own: assessor and admin are one place with tabs inside it.
R3 The submitter side and the assessor side are separate products that share a build. Neither screen may describe the other, and no state carries between them. Agreed Mariia owes this They are on one page today for testing, and the crossover links exist for that reason alone. R2 The views are separate. A submitter cannot reach the assessor view or the admin view. Built They are reachable from one page today so the shape can be shown and argued about. That is a property of the prototype.
R3 The admin adds assessors. Signing in tells the tool which role somebody has, and they never choose it themselves. Agreed
R4 The admin can grant admin rights to an assessor, the way a Discord server grants a role. Agreed So an admin leaving does not leave the programme without one.
R5 Rights decide which settings somebody sees. Agreed
R6 The exact rights each role carries, as a table, before any of it is built. Proposed The Discord model is the reference: named roles, each with a set of permissions, granted per person.
R7 What an assessor sees of the pool. Open Dan or Chris owes this Every assessor sees everything today. Chris says departments know who their assessor is, so a department could pick one at submission, and an assessor could share a file or hand it on. R8 Whether admin is a role of its own or an assessor with more buttons. Open Dan owes this
R9 An admin can delete a record, and has to type the initiative name out to do it. Built Copied from the way GitHub deletes a repository. A prototype fills up with test submissions and somebody has to be able to clear them; the protection is the typing, because a confirmation somebody can agree to by reflex stops being one.

3. Signing in

The thing that makes every access rule above enforceable.

S1 Real sign-in, so the tool knows who somebody is without asking them. Agreed The no-sign-in design came from the assumption that the tool would hold classified evidence and therefore could not be online at all. P3 removed that assumption, so the constraint went with it.
S2 For the real thing, the departmental account: the same one used for Teams. Agreed Microsoft Entra. No new password, and the tool knows the person and their department from the sign-in.
S3 For the prototype, sign in with a Google account, which sends no email and needs no password. Built The first plan was a link sent to a work address. Firebase caps that at five sign-in emails a day for the whole project on the free plan, which is three testers, so it cannot be the prototype route. Neither of these sends an email at all. Microsoft matters because it is how Dan tests from his work account, and it may need TBS to allow the sign-in, which Google does not.
S6 Microsoft sign-in, so Dan can use his work account. Proposed Dan, then TBS owes this The button is on the screen and the provider is not enabled: Firebase needs an application registered in an Azure directory, which needs somebody with Azure rights at TBS. Google works meanwhile.
S7 Every address the page is served from is registered against the sign-in, in two places. Built Firebase authorised domains, and the OAuth client’s authorised redirect URIs and JavaScript origins in Google Cloud. Missing the second gives redirect_uri_mismatch and nothing else explains it. Publishing the tool at a new address means adding it in both places.
S8 The Firebase web key answers only from the addresses the tool is served from, and only for the three APIs it uses. Open Mariia owes this The published page carries the key, which is how Firebase is meant to work: it names the project and authorises nothing by itself. GitHub secret scanning flags it anyway, because the same shape of key can carry billable access on other Google APIs. A command-line call reached the project with no site attached, so the key today carries no restriction. The restriction to write is websites myermcat.github.io and localhost, APIs Identity Toolkit, Token Service and Cloud Firestore. What guards the data is the sign-in and the published rules, so this is about somebody else spending the project’s free quota.
S4 Until sign-in exists, the assessor side opens on a screen shaped like a sign-in that says it is a mockup, and everything it produces is labelled unverified. Built
S27 A record named before codes were readable is given a code somebody can be told, on its next save. Built Mariia owes this Found on 17 September by the one person with a record older than the change. Ids were twenty characters over a 62-symbol alphabet until 14 September. The screen put that name through the code formatter, which uppercases, drops every character the current alphabet excludes and keeps the first twelve, so the results page showed a twelve-character code that named no document. She copied it off her own screen, typed it into Open with an access code, and was told no assessment has it, about an assessment she had just saved online and watched the badge confirm. The formatter now shows a name it would not have minted exactly as it stands, and the next save mints a readable code and writes the record under it. The old document is left where it is, unreachable, which is what it already was: deleting it is an admin’s right and the page does not have it. The name it had is kept on the record as previousId so the copy left behind can be matched to the one that replaced it. The test that let this through asked looksLikeCode, which tidies what a person typed before judging it, so a twenty-character mixed-case name tidied down to twelve characters that were all in the alphabet and answered yes. Judging a stored name is a different question and now has its own function.
S25 One code per assessment, minted when it is created, called the reference code. Built Decided 14 September, replacing two codes with one. There was a four-character reference minted at creation for email subject lines, and a twelve-character access code minted at the first online save. Same alphabet, both called a code, sitting centimetres apart on the results page: "give me the code" had two answers. The merged code is minted at creation, which is what the short one always did, so an assessment can be named before it has ever been online and somebody who types a code for an assessment that was never saved is told that in those words. Email subjects quote its first four characters only: a subject line is logged, forwarded, quoted back in replies and answerable to access-to-information, and the whole code opens the assessment. Four characters finds the thread in Outlook and is eight characters short of opening anything. It is never rotated or swapped, because with no owner there is nobody who could be allowed to do it without also letting anybody lock everybody else out.
S26 Anything that replaces the assessment this browser holds makes you tick a box saying you have kept the code. Built Asked for on 14 September. The sentence was already on the window and a sentence is something people scroll past; the act of ticking is deliberate in a way reading is not, and the code is beside the box to copy. The same window refuses to commit until it is ticked, and it shakes when somebody presses the button anyway, because a refusal that only adds a line of text is a refusal people miss.
S27 A work email is refused unless it ends in gc.ca or canada.ca. Built Changed from a warning on 14 September: a grey line beside the field is read by nobody who did not already know, and a save under a wrong address is a version attributed to somebody who cannot be found. Every federal department is under gc.ca, including the Senate at sen.parl.gc.ca, which is why this is a suffix and not a list of departments that would go stale. An address that differs from the one this browser last saved with is called out beside the field, which is the only defence against somebody accepting the remembered address, deleting half of it by accident and pressing Enter.
S23 Anything that replaces the assessment this browser holds asks first, offers to save it online, and says what would otherwise be lost. Built One guard, src/guard.ts, used by all five paths that replace the draft: opening a file, opening by access code, switching question set, discarding, and undoing a discard. It was five windows saying five different things. Three asked and offered a file, one asked and offered nothing, and opening by access code asked nothing at all. Three states: work never saved online has everything to lose, work saved online and edited since has the edits to lose, and an empty form asks nothing, because a window in front of nothing is how people learn to dismiss windows.
S23 Saving online asks who is saving: a name and a work email, every time, kept with that version. Built Dan, 14 September. A version used to arrive with nobody attached to it: the owner address is set once when the record is created, and somebody holding the access code left no trace, so an assessor could not tell whose work was in front of them. Typed and checked by nobody, and every screen showing it says unverified, the same way the assessor’s own name always has. Checking it would cost every submitter an account, which is the thing Dan does not want. The browser remembers the last pair and offers them as grey placeholder text: one Tab accepts both and moves to the button, Enter presses it. Offered rather than filled, because a filled field is a claim the tool makes on somebody’s behalf and the second person on a shared machine would save under the first person’s name without reading it. The record keeps the last twenty saves as the version trail the tool has, since a save replaces the document.
S24 The email check refuses only what is not an address at all. Built There is no single Government of Canada email domain. The published Email Management Services Configuration Requirements give every public servant two addresses, one at their department and one at canada.ca, and the departmental half differs for every department. The Senate is at sen.parl.gc.ca, two levels below gc.ca; Canada Post is not on gc.ca at all. Duplicate names get a digit, middle initials add a segment, generic mailboxes look nothing like a person. So the blocking rule asks only that it be an address, and an address that is not gc.ca or canada.ca gets a line beside the field saying it will be saved as typed. A form that turns away a real public servant is the worse failure here, because nobody verifies the name anyway.
S21 An assessment carries an access code, which is its own name in the store, twelve characters in three groups of four. Built The id and the access code are one value, because the id is the document path and knowing a path is exactly what "may open this one record and nothing else" means. A separate code would need a lookup table and two things to keep in step. Twelve characters from a 32-symbol alphabet with I, O, 0 and 1 removed is 2^60: thirty-six years of guessing at a billion a second, and about a one in a billion chance any two collide at 50,000 assessments. It was twenty characters from a 62-symbol alphabet, which is stronger and unreadable, and somebody has to carry this one over Teams and read it down a phone.
S22 The access code is typed into one box per character, and everything a person might reasonably do with it works. Built Paste the whole code into any box with or without dashes and in any case, type it straight through with the focus moving on by itself, backspace out of an empty box into the one before, and arrow between boxes. The dashes are drawn and never typed, and they are hidden from a screen reader, which would otherwise read them as words. A field people fight with is a feature nobody uses.
S18 A submitter reaches an assessment with a share code and no account. An assessor and an admin need an account. Agreed Mariia, then Dan owes this Decided on 10 September, after Dan asked whether the tool needs accounts at all. The answer is split, and the reason is mechanical. Firestore rules can read a query’s limit, its offset and its ordering, and nothing about a filter, so no rule can permit "list the assessments matching the code I typed". The only list rules available are an identity test or one that permits everybody, and permitting everybody publishes every department’s draft to anybody who reads the page source. Delete is worse: it is the one destroying right in the tool, so a self-declared admin empties the store. Everything else an account was doing for a submitter, a code does as well or better, and it fixes one thing accounts made worse: today a submitter reaches their own record only through an id in one browser, so clearing a browser loses a submission to its own author.
S19 Both routes stay in the build, and one input picks which one answers. Built EARB_ACCESS takes accounts or code, defaults to accounts, and refuses anything else in one sentence. src/who.ts is the single interface every screen asks: who this is, whether the name has been checked, and whether this person may list the pool. Both paths stay compiled, typechecked and covered, because commented-out code is none of those and code that is not typechecked has been abandoned and not kept.
S20 What a share code must do before it may grant a write. Open Mariia owes this Partly answered on 17 September. The rule granting update on the code went live that day, and the field mask went in the same day: a save names the fields it changes, so the accidental half of this, two code-holders overwriting each other, is closed. The deliberate half is not, and it needs a rule refusing a write that empties a question. It is acceptable while the people holding codes are three testers, and it is the first thing to answer before anybody outside that group is sent one. Three things stand in front of it, all found on 10 September. A code that grants update is a blanking key: a rule permitting whoever holds it cannot tell a legitimate save from somebody clearing 176 answers, and putAssessment writes the whole document with no field mask, so two code-holders typing at once is last-write-wins over an entire assessment. A8 was a nicety and becomes a precondition. An open read rule also lets an unauthenticated loop spend the whole daily allowance and take the tool offline. And A5, that an assessor cannot change the evidence, survives only if the audit moves to its own document beside the assessment, which the published rules already describe and nothing has ever written to.
S14 An assessment is complete when every question in its set carries a score or is marked not applicable, and the six overview fields are filled. Agreed Decided on 8 September. The overview counts as things that have to be filled in, and not as questions: the count on screen stays 176. No floor on how much may be marked not applicable, because an assessment that is not applicable throughout is a thing an assessor should see and judge. The reasoning and the evidence are excluded: no question asks for either, and requiring them would buy typed filler, which the flags already catch from the other direction.
S15 An assessor may read an unfinished submission and may do nothing else with it. Agreed Decided on 8 September. No scoring, no verdict, no questions written against it until the submitter says it is finished.
S16 Whether saying an assessment is finished stops the submitter editing it. Open Mariia owes this Left open on 8 September, with a leaning towards yes: a locked assessment is how an assessor knows they are not scoring a moving target. What it costs is that a typo becomes a request to somebody else. The alternative, which is what happens today, is that the submitter keeps editing and the assessor screen marks the row as updated.
S17 Only an admin grants a role. An assessor cannot make somebody else an assessor. Built The published rules allow create and update on a role document to an admin alone, and no delete to anybody, so nobody can promote themselves or each other. Today that means every assessor account has to come from you.
S9 An account that signs in without an assessor role is told so, by name, with a way onward. Built Signing in and being allowed in are two different things. An address nobody has added used to reach the assessor screen and be told the pool was empty, which reads as a lost submission. It now gets one screen: what happened, the address to send to an admin, a way back to the home page, and a way to sign in as somebody else. An assessor who asks for the admin view is turned back the same way.
S10 Sharing an assessment is handing somebody its access code. Whoever holds the code can open it and change it, and nobody without it can. Built This replaced a mockup that asked for email addresses, recorded them and granted nothing, which the user found beside the real mechanism and asked which of the two was working. The code is the record’s own name in the store, so there is one thing to share and one thing to hold. It appears as a control you can copy from everywhere it is shown: the results page, the window behind File, the first online save, and every window that might replace the assessment in this browser. The tool sends nothing, and says so wherever the code appears.
S21 Telling somebody about an assessment happens outside the tool. Agreed Mariia owes this Decided 14 September. The tool cannot put a message in front of anybody and must never look as though it has. It can open the person’s own mail client with the message and the code already written, which is their client sending, not the tool. The only control that touches an assessor is a mark on the record.
S22 A code cannot be taken back. Agreed There is no list of who holds one and no way to withdraw it. Somebody given the code keeps the ability to open and change the assessment, and forwarding it passes the same ability on. Said on the sharing window and in settings, in those words. Withdrawing access would mean a new code and a new record, which is a decision nobody has needed yet.
S11 Somebody holding an access code may open that one assessment and change it, with no account. Built Mariia, then TBS owes this Published on 17 September, and checked from outside the same hour: deploy/check-rules.sh with no sign-in at all refuses listing the collection, listing with a page size, reading the roles, creating an assessment and making yourself an admin, and opens one by its code. Until it was published the tool minted a code, showed it, let somebody type it, and Google refused the request, so the code meant nothing on its own. Written on 14 September in deploy/firestore.rules: get on an assessment is granted to anybody who can name the document, because the name is the code, and update is granted on the same basis with the owner’s address, the document kind, the assessor’s verdict and the withdrawal frozen. Listing still needs an account, which is the property that matters: a stranger may open the one assessment whose twelve characters they were sent and may never ask what else is there. The arithmetic is 2^60. Publishing is one paste into the Firebase console by whoever owns the project, and deploy/check-rules.sh checks the result from outside, including that listing is still refused.
S12 Holding a code never grants scoring. Agreed The audit is gated on a role document that only an admin writes. If the code widened that, anybody could appoint their own assessor by sending them a code.
S13 Whether an assessment is routed to one named assessor. Open Dan owes this Every assessor can already list every submitted assessment, so naming one would be a routing hint and not a permission. Which of the two it is changes what the assessor screen should show. With no naming, the submitter sends their assessor the code and the routing is the message.
S5 A submitter may read and change their own submission, and no other. Agreed And any submission they have been added to.

4. The instrument

The questions, the weights and the scale. Dan owns the content; the tool renders whatever it is handed.

Q6 A question belongs to its own domain and to any number of named categories. All nine categories TBS named are declared. Built Business, Data, Application, Technology, Security, Privacy, Financial, Accessibility and Official Languages, asked for by Dan on 8 September. A question carries a topics array; it counts once in the overall score through its domain, and at full weight inside every topic it carries, which is what lets security weigh differently from business without inflating the total. 44 of 176 carry more than one today. The results page shows the second cut as its own set of bars and says in one line that they do not add up to the overall.
Q9 Dan gives his own category assignments in a Topics column in the workbook, and the importer reads it. Built Added 14 September. One column per domain sheet, headed Topics, found by its header so it can sit anywhere; the cell holds the categories beyond the question’s own domain, comma or semicolon separated, matched without regard to case or spacing; a blank cell means the question is only about its own domain, which is the common case and costs nobody any typing. A name that is not one of the nine refuses the whole import and says which question and which name, because a mistyped category is the one error nobody can see afterwards: the question counts towards nothing and every screen still renders correctly. The rubric loader refuses the same thing when a file is opened. Until all four sheets carry the column the tool falls back to a keyword pass over the question wording and calls the grouping provisional on every screen that shows it; the badge goes when the column does all four.
Q10 The category assignments themselves. Open Dan owes this The mechanism is finished and waiting. All five categories that are not domains are read from the wording of each question and are ours, not his: Security 25, Privacy 8, Financial 13, Accessibility 3, Official Languages 2. Accessibility and Official Languages were reported as empty on 14 September and that was wrong, corrected on 17 September: the sweep counted hits without reading them. Six questions mention something accessible and three are about accessibility; the other three are the FAIR principles’ Accessible and data reaching other departments. The pattern now matches the noun and WCAG and not the adjective. Both categories are thin rather than absent, which the results page says beside the bar, because a score built on two questions moves a long way on one answer.
Q11 Which questions are answered yes or no rather than scored. Open Dan owes this Dan named the defect and gave one example. Ten of the 176 read as binary and are marked so in the question set, from a narrow pattern over the wording, which is ours. The workbook now carries an Answer type column holding our reading, with the Answer column beside it offering the matching picker: 0 to 10 for a scale question, Yes and No for the others, N/A on both. Confirming or overruling ten rows is the whole of the ask.
Q1 The question set is a data file. A new version is a new file, and every assessment records the version it was answered against. Built
Q2 Question sets accumulate. Adding one changes nothing on its own; one set is active at a time; any set can be previewed, made active or deleted. Built
Q3 A submission is scored against the set it was answered against, and the row says which set produced the number. Built
Q4 Each question is scored 0 to 10 against a ladder of descriptions, and the ladder is visible while answering. Built
Q5 Question weight is multiplied by a lifecycle-stage factor, and the weights are re-normalised so every assessment still scores out of 10. Built
Q6 Not applicable is an answer. It leaves the score out of every total and counts as dealt with for progress. Built
Q7 Ten questions are yes/no. A no colours its question, its section, its rail row and its domain tab, and stops nothing. Proposed Dan owes this Which ten is our reading of his wording, and is labelled provisional in the tool.
Q8 Questions carry topics as well as a domain, so the same answers can be cut across the four domains. Built Dan owes this Six topics, 31 questions in two of them. A question counts fully in each topic and once in the overall, so the topic scores do not add up to the overall.
Q9 Per-question criticality, separate from section weight. Open Dan owes this
Q10 The dropdown answers for each question. Open Dan owes this None exist. The only real source is the 700-odd past assessments.
Q11 The Business Architecture section weights add up to 80. Open Dan owes this His own workbook, confirmed in his words. The tool shares the missing 20 out proportionally and shows the normalised share.
Q12 The routing thresholds. Open Dan owes this He gave three different numbers in one conversation. The tool interpolates and labels the threshold provisional wherever it appears.

9. Data, storage and hosting

Where the answers live.

H1 Work is kept in the browser as it is typed, and can be saved to a file and reopened. Built

Risks we have accepted

What could go wrong that we are choosing to carry, why it is bearable at this stage, and who said so. A risk leaves this list when it is mitigated or when it stops being possible.

RK1 Low

Somebody scripts requests against the store and takes the tool offline.

BecauseThe rule that makes an access code work grants a read on the document’s name, so an unauthenticated request reaches the store. Nothing in Firestore rate-limits by address, security rules cannot count, and the free plan has no spend cap and no alert unless the project is upgraded to pay-as-you-go, which is a decision for TBS and not for us.

If it happensTwo different failures. The daily read allowance is 50,000 and resets overnight, so the tool stops answering until midnight Pacific. The monthly one is 10 GiB of outbound traffic, which at 41 KB an assessment is about 256,000 reads, and exceeding it turns Firestore off for the rest of the calendar month with no remedy but upgrading mid-incident. Nothing is lost and nothing is exposed either way.

What we doAccepting it, and the reasoning changed on 14 September when the numbers were checked. Listing is what makes this cheap for an attacker, and listing still needs an account: without it a script has to name a document, which is twelve characters from a 32-symbol alphabet, and 2^60 guesses is not a route to anything. App Check was the conventional answer and was examined and rejected: it cannot be expressed in a security rule, it needs a third-party script from Google on a page whose whole policy is default-src none, it draws a badge that lands in the accessibility audit of a Government of Canada service, its free tier is 10,000 assessments a month for the whole organisation and it spends them on a refresh timer rather than per visit, and Google documents the header it rides on only for backends you own and never for the Firestore REST API, so there is no published evidence it would apply to this page at all. Anonymous sign-in was examined and rejected too: it costs an attacker one extra request and adds a second endpoint that can be flooded, whose only kill switch is the feature itself.

Accepted byMariia, 14 September 2026

RK2 Medium

An access code reaches somebody it was never meant to reach, and cannot be taken back.

BecauseA code is a bearer token: whoever holds it opens that assessment and can change it. Forwarded once it is permanent, there is no list of who holds it, and there is no way to mint a new one for the same record.

If it happensOne assessment is readable and writable by one more person than intended. The assessment itself is Unclassified, and what it holds is typed reasoning and the titles and locations of evidence, which can name artefacts marked above Unclassified even though no such artefact is kept in the tool. Treat a leaked code as a disclosure of the assessment.

What we doSaying so plainly, in those words, on the sharing window and in settings, so nobody learns it from an incident. A revocation switch was designed and rejected on 14 September: the page sends the whole document on every save, so any save from a copy that predates the switch would have deleted it and turned the code back on with nothing on screen saying so. A control that reports success without firing is worse than none. The real answer is code rotation, which means a new document and a new code, and it is the next thing to build here.

Accepted byMariia, 14 September 2026

RK7 Low

Somebody scripts the creation of assessments and fills the free storage.

BecauseAn assessment has its code before it has ever been online, so the first save is a create by somebody who may have no account. Requiring one would put the account back on the submitter, which is the thing this design removes.

If it happensDocuments nobody wants, against 20,000 writes a day and 1 GiB. An admin deletes them.

What we doThe store asks for two things on a create, and neither is a security control: the document name has to be a code this tool would mint, and the body has to carry the five parts of an assessment. They stop the collection being used as free storage for something else. Nothing in Firestore rate-limits by address and security rules cannot count, so there is no version of this that is closed rather than expensive.

RK8 Certain

The trail says who saved a version and not what changed in it.

BecauseA save replaces the document. Keeping whole versions would mean 41 KB each inside a record that has to stay one document.

If it happensAn assessor can see that a score moved between two saves and cannot see which answer moved it without asking.

What we doThe trail keeps who, when, what it scored and how many questions were answered, which is enough to see a number move and to go and ask the person who moved it. Twenty saves, and when it fills, the ordinary ones go first: the save where the assessment first reached TBS and every time it was marked ready or unmarked are kept, because those are the ones somebody asks about. Answer-level history needs a subcollection and is its own piece of work.

RK9 Low

Somebody holding a code empties an assessment, and every answer is gone.

BecauseThe published rules grant update to whoever can name the document, and the name is the code. A rule cannot tell a legitimate save from somebody clearing 176 answers: it sees one write of one document by somebody entitled to write it. putAssessment sends the whole document with no field mask, so the ordinary save already replaces everything, and an emptied assessment is a save like any other. Two people typing at once is the same mechanism without the malice, and the later save wins over the whole record.

If it happensAn assessment is back to blank, in the store, where the assessor reads it. The browser that did the emptying has the blank version too, so reopening it recovers nothing. Anybody else who still has the work on their own machine can save it back; if nobody does, it is a rebuild from the file somebody last saved, and if nobody saved a file it is 176 questions answered again.

What we doHalf built on 17 September, and the built half is the one that was going to happen by accident. A save now names the fields it changes and Firestore leaves the rest of the document alone, so two people working from one code no longer overwrite each other by taking turns pressing Save, and a save can no longer carry away an answer nobody touched. The comparison is against what that browser last sent; a browser that has never sent this record reads the document first, which costs one read and is the only way to know what is being left alone. What is still open is the deliberate version: somebody who means to empty an assessment can mask every answer and send nothing under each path. That needs a rule refusing a write that empties a question, and it is a rule that can be written. The save trail shows the drop afterwards, because it records how many questions each save left answered, and it holds nothing that could put them back.

RK5 Low

BecauseThe code grants a write, which is what sharing means here, and the tool cannot tell a co-author from a stranger who was forwarded the message.

If it happensAn answer, a justification or a piece of evidence is different from what the owner left, with nothing on screen saying who changed it.

What we doFour fields are frozen against anybody who is not the owner, and Google enforces it rather than the page hoping: the owner’s address, so a record cannot change hands; what kind of document it is, so it cannot be hidden from the assessor’s list; the assessor’s verdict; and the withdrawal. The five structural parts of the document must all be present, so a one-field write cannot reduce it to a stub. What is deliberately not frozen is the ready mark, because a co-author holding the code is somebody working on the assessment. There is no per-field history, and adding one is the version-history work that is already on the list.

How each requirement gets checked

Four gates run on every change, and a requirement is not built until the gate that covers it passes. A fifth runs against the live store when the rules change.

The prose gate. Every word the reader sees is checked against the writing rules: no em dashes, no antithesis, no banned words. It runs before the tests and fails the build.

The logic gate. Scoring, banding, weighting, the flags, the CSV round trip. It runs against the modules directly.

The interface gate. The built page is driven in a real document object model, end to end: 21 pages of questions answered, evidence attached, markings set, dialogs opened and their buttons pressed. Around 500 assertions, and this is where a requirement about behaviour is actually held.

The print gate. A printed assessment is checked for the things that vanish on paper: the scores, the reasoning, the marking, and every folded section.

The rules gate. deploy/check-rules.sh calls the live store four times with no sign-in at all: read every assessment, read the roles, write an assessment, make yourself an admin. All four have to come back refused. A rules mistake cannot be seen from inside the tool, because the tool always has somebody signed in, so this one runs from outside. As of 3 September all four are refused.

What no gate covers: anything needing a sign-in or a second person. Those requirements are marked agreed, and they say so.
