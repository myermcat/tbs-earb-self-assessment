The submitter page and the assessor page share one browserNext Found while working out why the demonstration page was showing real work. The demonstration has its own names now. The two real pages still share every name with each other, because they are one origin, and one of them acts on it: activating a question set on the assessor side clears the submitter’s draft in the same browser, with no warning and nothing to undo it. Discarding a draft says the browser is holding nothing, and it isNext Also found in that sweep. Every assessment this browser has ever saved online leaves a full copy behind under its own name, and nothing in the tool ever removes one. The window that discards a draft says what it is taking away and that copy is not in the list, so the sentence is untrue in the one place somebody reads it to decide.
The assessor’s audit never reaches the storeNext The biggest one. An assessor scores a submission and the only thing that happens is a file downloads to their laptop. So the portfolio’s audited count can never leave zero, and a review exists nowhere the department can see. It is a decision before it is a patch: the published rules describe the audit as a separate document beside the assessment, so an assessor can write a score without being able to touch an answer, and the code keeps it as a field inside the assessment, which the rules refuse to let an assessor write at all. One of the two has to move. Writing it where the rules already allow means a second small write beside the assessment; keeping it as a field means widening the rules so an assessor may update the document, and then something has to stop them editing answers.
Nothing tests the sign-in round tripNext Every test seeds a session by hand, so the three legs of a real sign-in are untested: asking Google for an address to send somebody to, holding the reference while the browser is away, and trading the code that comes back for a token. That is the one leg that reached you broken, twice.
The rules are only ever tested signed outNext deploy/check-rules.sh makes four calls with no account and asserts all four are refused, which is worth having. What nothing covers is the part that matters once there are two departments in the store: that one submitter cannot read another’s assessment. Proving that needs two signed-in identities, which means the Firebase emulator and its rules-testing library, run from the tests.
The question-set lock only warns, and its own importer overwrites itNext rubric/rubric-ids.lock.json records what each of Dan’s 176 question ids meant, so that a question changing meaning while keeping its id can be caught. Every assessment records the ids it answered, so a changed meaning makes old scores wrong without anything looking wrong. The lock only prints a warning, it is not part of npm test, and the importer rewrites it at the end of its own run, so a drift is absorbed after one pass. Reading it in the tests and failing on a changed meaning is half an hour.

Resolved questions

Settled, and how.

Can the assessor side work on a code, the way the submitter side does?
Resolved. No, and it was worked through rather than waved away. The legal half is real: a rule can grant read on a named document, so a roll-up document named by a long code would be a lawful thing to read, and each submitter could be confined to writing their own row into it. It fails on what a leak costs. One assessment code leaks one assessment. An index code leaks every department at once, and it cannot be rotated, because its address is compiled into every published submitter page: old pages keep writing to the old document and anybody holding an old build keeps the address. Loosening the write rules enough to make it work also removes the one thing that lets a reader tell afterwards whether a verdict was written by an assessor or by the department being assessed, which takes the audit out of evidence.
Should the tool hold classified information?
Resolved. No. Nothing protected or classified goes in at all, settled with Dan on 1 September. That removed the second deployment, the local-only engine, the theme switch, and the whole recall problem.
What happens to online data when a marking rises?
Resolved. Dropped. The tool never stores classified evidence, so the question cannot arise.
Does a two-topic question count twice overall?
Resolved. No. Once in the overall score, and at full weight inside each topic, which is where the weights genuinely differ.
File sharing for a team filling one in together?
Resolved. No files. Everything is online, so version control stops being a problem the tool has to solve.
Deletion rights
Resolved. Nothing is ever hard-deleted. A record is withdrawn and left out of the statistics.
One build or two?
Resolved. One. Submission is a capability the hosting turns on.
Where the plan lives
Resolved. This page. The Markdown version is deleted.
Org access to canada-ca
Resolved. Done. Nick invited you, and the TBS-OCIO-ESP team gives push access to canada-ca/TBS-OCIO-ESP.
Who may replace the question set?
Resolved. The assessor and admin side only. Loading one clears every answer, so a submitter is told where it lives and not handed the control.
How does the dashboard stay current?
Resolved. By storing nothing. It recalculates each record from its answers as the page draws, so there is no roll-up that can go stale.
